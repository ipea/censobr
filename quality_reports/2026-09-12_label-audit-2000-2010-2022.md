# Label audit — `add_labels_*()` vs microdata, by census year

**Status (2026-09-13):** all CRITICAL and MAJOR findings fixed except M1, which is a deliberate
choice — `tests/testthat/test_labels_households.R:66-73` asserts that the `"."` sentinel of
`v1111`-`v1113` stays `NA`. C2, C3 and M8 were fixed by the maintainer; C1, M2-M7 and M9 in this
session (see `NEWS.md` dev bug fixes and the new regression tests in `tests/testthat/test_labels_*.R`).

**Date:** 2026-09-12 · **Branch:** dev (uncommitted working tree) · **Data release:** v0.7.0
**Method:** three independent auditors, one per year. Each parsed every `case_when` / `across()` /
`if_else()` arm out of the labeller AST (never retyped), then compared the code sets against
(1) the distinct raw values of every labelled column in the parquet files (lazy arrow, `count()`,
never a full `collect()`) and (2) the official IBGE microdata dictionary xlsx for that year.
2022: no real controlado parquet exists on this machine, so the dictionary is the only ground
truth; the fixture in `inst/extdata/` was used solely for column names/types and a smoke test
(its Pessoas codes are generated from the labeller itself, so agreement is circular).
Orchestrator re-verified all CRITICAL claims against the source (and the V4001 raw codes).
Scratch scripts: `%TEMP%\claude\R--Dropbox-git-censobr\854f3891-…\scratchpad\y{2000,2010,2022}\`.

## Incidental (out of scope, worth a follow-up)

`arrow_open_dataset()` (`R/utils.R:204-222`) calls `unlink()` on the cached parquet whenever
`arrow::open_dataset()` throws. During the parallel run a transient Windows file lock triggered
that path against the 800 MB 2010 population file; the unlink failed and the retry succeeded, but
on a system without the lock any transient open error would delete a valid cache file.
